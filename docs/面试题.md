# 汽车知识问答系统 v2.0 · 面试题库

> 项目定位：基于 Flask 的汽车领域知识问答系统，支持本地 bge-m3 向量 RAG 检索回答（余弦相似度 + SQLite 向量缓存）、大模型 API 接入（智谱 GLM / OpenAI，界面直接配 Key）、问答记录管理、知识库管理与多格式导入、用户反馈入库、管理后台登录鉴权。
>
> 代码位置：`汽车知识问答系统代码/app.py`（约 792 行，路由/数据库/问答/RAG/大模型调用）、`汽车知识问答系统代码/rag.py`（125 行，嵌入与检索）。以下所有数字均核对自源码。

## 一、项目定位与 RAG 原理

### Q1. 介绍一下这个项目，为什么要在汽车问答里引入 RAG？

**考察点**：项目全貌、RAG 解决什么问题、与传统检索式问答的区别。

**答案要点**：
- 项目是 Flask + SQLite 的汽车领域问答系统，单机可跑，无需外部向量数据库。
- 传统关键词匹配只能命中"问法完全一致或包含"的问题；引入 RAG（bge-m3 嵌入 + 余弦相似度）后，"问法不同但意思相同"的问题也能命中知识库（`app.py` 的 `get_answer()`）。
- 整体回答策略按优先级四级递进：① RAG 语义检索（相似度 ≥0.55 直接返回知识库答案）→ ② 嵌入模型不可用时回退关键词匹配（精确 → 双向包含 → 关键词，`keyword_match()`）→ ③ offline 模式返回 5 条内置关键词规则答案（开箱即用）→ ④ zhipu / openai 模式调用 OpenAI 兼容接口，并把检索到的前 3 条相关知识注入 system prompt（简单 RAG 增强）。
- 亮点：本地嵌入（数据不出机）、向量持久化（重启不重建）、界面配 Key（无需改环境变量）、优雅降级（模型目录缺失时功能不中断）。

**文件位置**：`app.py` L431-461（`get_answer`）、L371-391（`get_offline_answer`）、L411-428（`keyword_match`）。

### Q2. 你的 RAG 流程是怎样的？有没有做 chunk 切分？

**考察点**：对 RAG 流水线的理解是否落到自己的实现上、能否诚实说明未做 chunk 的原因。

**答案要点**：
- 流程：用户问题 → 从 SQLite `knowledge` 表取全部条目 → bge-m3 编码知识条目（带缓存）与问题（均 `normalize_embeddings=True` 归一化）→ 归一化向量点积即余弦相似度（`mat @ q`）→ `np.argsort(-scores)[:top_k]` 取 top 3。
- **没有做 chunk 切分**：知识条目本身是人工维护的"一个问题 + 一个答案"短文本（QA 对），粒度天然合适，直接以"条目"为检索单元；编码内容是 `question + '|' + keywords` 的签名串（`rag.py` 的 `_signature()`），答案不参与编码。
- 权衡：若知识条目变成长文档（如整篇维修手册），就必须引入 chunking（按段落/固定窗口切分 + overlap），这是当前架构明确可扩展的方向。

**文件位置**：`rag.py` L45-46（`_signature`）、L95-125（`search`）。

## 二、bge-m3 嵌入与检索

### Q3. 为什么选 bge-m3？嵌入维度是多少？如何加载的？

**考察点**：嵌入模型选型理由、模型加载的工程细节。

**答案要点**：
- bge-m3 是多语言（含中文）嵌入模型，输出 **1024 维**向量；本地部署（`SentenceTransformer(MODEL_PATH, device='cpu')`），数据不出机，无 API 成本。
- 默认路径硬编码 `D:\models\bge-m3`，可用环境变量 `BGE_M3_PATH` 覆盖（`rag.py` L18-19）。
- 模型单例懒加载：模块级 `_model = None`，第一次提问时才加载（CPU 约 15 秒），之后不再重复加载；`is_available()` 只检查模型目录是否存在。
- 依赖 `sentence-transformers` + `torch`（CPU 版即可，安装约 2GB）。

**文件位置**：`rag.py` L18-19、L28-37。

### Q4. 向量缓存是怎么实现的？重启服务后为什么不用重新编码？

**考察点**：增量计算的工程意识、内容签名失效策略。

**答案要点**：
- 向量持久化在主库同一 SQLite 文件的 `knowledge_vectors` 表：`knowledge_id INTEGER PRIMARY KEY, signature TEXT NOT NULL, embedding BLOB NOT NULL`（float32 `.tobytes()` 存 BLOB）。
- **内容签名 = `question + '|' + keywords`**（`_signature()`）。检索时先加载所有与当前签名一致的缓存向量（`_load_cached_vectors`），**只对"id 没有缓存向量"（新增或签名变化）的条目重新编码并 `INSERT OR REPLACE` 写回**，实现增量更新。
- 已删除条目的残留向量在每次检索时用 `_delete_stale_vectors(valid_ids)` 清理（`DELETE ... WHERE knowledge_id NOT IN (...)`）；内容变化但 id 保留的向量由签名比对天然失效。
- 效果：服务重启直接复用向量，只有新增/修改过的条目才付出编码成本。

**文件位置**：`rag.py` L45-92、`app.py` L107-111（建表）。

### Q5. 相似度怎么算的？阈值是多少？两个阈值各起什么作用？

**考察点**：是否清楚"归一化点积 = 余弦相似度"以及双阈值设计。

**答案要点**：
- 知识向量与问题向量均 `normalize_embeddings=True` 归一化后，`mat @ q` 矩阵点积在数学上就是余弦相似度（0~1），`np.argsort(-scores)` 降序取 top_k=3。
- **阈值一 `RAG_SIM_THRESHOLD = 0.55`**（`app.py` L394）：top1 相似度 ≥0.55 视为知识库直接命中，不调大模型，直接返回答案，来源标识为 `'知识库RAG · 相似度%.2f'`（前端展示实际相似度）。
- **阈值二 0.30**（L456）：未达 0.55 时，若有大模型（zhipu/openai），把相似度 ≥0.30 的检索结果拼成 `【问题】答案` 上下文注入 system prompt（最多 3 条）。
- 注意细节：若 `rag_search` 返回 None（模型不可用/异常）才回退 `keyword_match`；RAG 可用但 top1 < 0.55 时**不会**再走关键词匹配，而是直接进入 offline / LLM 分支——这是有意为之（语义检索已覆盖关键词场景）。

**文件位置**：`app.py` L394、L437-461、`rag.py` L120-125。

### Q6. 如果嵌入模型目录不存在或加载失败，系统会怎样？

**考察点**：优雅降级设计。

**答案要点**：
- `is_available()` 只做 `os.path.isdir(MODEL_PATH)` 检查；`rag_search()` 里 try/except 包住整个导入与检索，任何异常打印日志后返回 None。
- 返回 None 后调用方走 `keyword_match()`（SQLite LIKE/INSTR + 逐条关键词拆分匹配），系统退化为"精确 → 双向包含 → 关键词"三级匹配，问答功能不中断；选 LLM 模式时则不带 RAG 上下文直接问大模型。

**文件位置**：`app.py` L397-408、`rag.py` L28-29。

## 三、LLM 接入与 Key 管理

### Q7. 支持哪些大模型？调用方式是什么？

**考察点**：OpenAI 兼容协议的理解、多模型切换。

**答案要点**：
- 支持两个服务商：**智谱 GLM**（默认 `https://open.bigmodel.cn/api/paas/v4/chat/completions`，模型 `glm-4.5-air`）和 **OpenAI**（默认官方地址，模型 `gpt-3.5-turbo`），均为 OpenAI 兼容格式，URL/模型名可用环境变量改指向其他兼容服务（Ollama、one-api 等）。
- `call_llm()` 用 `requests.post` 发 `/chat/completions`，messages = system（"专业汽车知识助手"人设 + 可选 RAG 上下文"请优先依据它们回答"）+ user（问题），`temperature: 0.7`，**timeout=30 秒**。
- 异常分层处理：Timeout → 提示超时；RequestException → 提示检查网络与密钥；KeyError/IndexError/ValueError → 提示返回不可解析。
- 返回的实际模型名取响应体 `data['model']`（可能与请求的 model 不同，如被网关改写），前端显示 `智谱GLM · <actual_model>`。

**文件位置**：`app.py` L43-50（配置）、L464-511（`call_llm`）。

### Q8. API Key 是怎么管理的？为什么可以不用重启就生效？

**考察点**：配置优先级设计、settings 表的读写。

**答案要点**：
- Key 有两个来源，**界面配置优先、环境变量兜底**：`get_api_key(provider)` 先查 SQLite `settings` 表的 `api_key_zhipu` / `api_key_openai`，没有再读环境变量（`API_KEY_PROVIDERS` 映射 provider → 环境变量名）。
- 管理后台 `/api_keys` 页面（需登录）粘贴保存，`/save_api_key` 用 upsert 写入 settings 表（`ON CONFLICT(key) DO UPDATE`），**立即生效无需重启**——因为每次 `get_answer` 都实时查库，不是启动时读入内存。
- 细节：已配置密钥回显只显示前 4 位 + `****` + 后 4 位；输入框留空提交即清除已保存密钥；密钥明文存储（README 已把加密存储列为优化方向）。

**文件位置**：`app.py` L151-174、L215-243。

### Q9. 前端的"模型已连接/未连接"状态角标是怎么实现的？

**考察点**：连通性探测思路。

**答案要点**：
- `/check_model` 接口：offline 直接 available；有 Key 时把 chat/completions URL 截掉 `/chat/completions` 换成 `/models`，带 Bearer 头 **GET 探测 5 秒超时**，HTTP 200 → available，否则 unavailable；未配置 Key 直接 unavailable。
- 前端据此切换分段选择器右侧的状态角标；未连接时提问会收到友好提示（"API尚未配置密钥…"）而不是报错。

**文件位置**：`app.py` L312-334、L477-479。

## 四、Flask 应用与鉴权

### Q10. 登录鉴权是怎么实现的？页面和 API 的未登录处理有什么区别？

**考察点**：session 鉴权、装饰器对页面/接口的差异化响应。

**答案要点**：
- 账号来自环境变量 `ADMIN_USERNAME` / `ADMIN_PASSWORD`，默认 `admin / admin123`（明文，README 已列为改进项：哈希存储）。登录成功写 `session['logged_in']=True` 与 username；`/logout` 清空 session。
- `login_required` 装饰器：已登录放行；未登录时按请求类型区分——**GET 且 Accept 含 text/html（浏览器）→ 302 跳登录页；fetch/ajax → 401 + JSON 错误**，前端不会拿到 HTML 当 JSON 解析。
- 保护范围：所有管理页面（/admin、/knowledge、/upload_knowledge、/api_keys）与管理 API（增删改知识、删问题、清空/导出知识库、导入）。
- 会话密钥：首次启动 `os.urandom(24)` 生成并写入 `data/.secret_key`，之后每次启动读文件——**重启后已登录 session 不失效**。

**文件位置**：`app.py` L20-27（secret_key）、L39-40、L179-210（鉴权）。

### Q11. 项目里 Flask 的 db 连接是怎么管理的？为什么这样做？

**考察点**：Flask 应用上下文、g 对象、teardown。

**答案要点**：
- `get_db()` 把连接挂在 `flask.g` 上，每个请求内复用一个连接（`row_factory = sqlite3.Row`），`@app.teardown_appcontext` 里 `g.pop('db')` 请求结束自动关闭。
- 每请求独立连接 + 及时关闭，避免多请求共享连接导致 SQLite 并发写坏文件（SQLite 单文件特性决定）；`rag.py` 里另用独立的短连接访问同一库文件。

**文件位置**：`app.py` L55-66。

### Q12. 问题记录里存了哪些字段？为什么 questions 表主键是 TEXT？

**考察点**：表设计与无序列生成。

**答案要点**：
- 每次提问（无论命中与否）都先落一条记录：`id`（**uuid4 生成的 TEXT 主键**）、text、time（`%Y-%m-%d %H:%M:%S`）、model（用户选的模型）、keywords（`extract_keywords()` 按标点/空白切词、保留长度>1 片段、逗号拼接）、type（'user_question'）。
- 用 uuid 而非自增：迁移自旧版 JSON（旧数据的 id 就是字符串），TEXT 主键兼容两代数据。
- 管理后台可查看/删除提问记录（按时间倒序）。

**文件位置**：`app.py` L80-87（建表）、L347-357、L364-367。

## 五、数据层（SQLite + JSON 迁移）

### Q13. 数据库有哪几张表？各自的职责？

**考察点**：对数据模型的整体掌握。

**答案要点**（6 张表，`init_db()` 建表，`CREATE TABLE IF NOT EXISTS` 幂等）：

| 表 | 职责 | 关键字段 |
|---|---|---|
| knowledge | 知识条目 | question/answer/keywords/source(manual/feedback/import_*)/created_at |
| questions | 提问记录 | id(TEXT uuid)/text/time/model/keywords/type |
| feedback | 用户反馈 | feedback_type/title/content/contact/time |
| import_logs | 导入日志 | time/message/status(success/error) |
| settings | 键值配置 | key/value（存 API Key） |
| knowledge_vectors | RAG 向量缓存 | knowledge_id(PK)/signature/embedding BLOB |

- 数据库单文件 `data/knowledge_qa.db`，首次启动自动创建。

**文件位置**：`app.py` L69-112。

### Q14. 旧版 JSON 数据是怎么迁移的？如何保证不重复迁移、不丢数据？

**考察点**：一次性迁移的幂等设计。

**答案要点**：
- 迁移对象四个文件：`knowledge_base.json`、`questions.json`、`feedback.json`、`import_logs.json`（feedback/import_logs 是代码支持但 README 未提的两个）。
- `_migrate_json()` 三重保护：文件不存在直接跳过；JSON 解析失败打印错误不中断启动；**目标表 `SELECT COUNT(*) > 0` 则跳过**——迁移只发生在表为空的首次启动，天然幂等，可重复启动。
- 迁移按列白名单 `str(r.get(c,''))` 取值逐行插入，非 dict 的条目过滤掉；**迁移后旧 JSON 文件保留不动**（不删除、不改写），方便回滚。

**文件位置**：`app.py` L113-145。

## 六、知识运营与反馈闭环

### Q15. 知识导入支持哪些格式？解析规则分别是什么？

**考察点**：多格式解析器的设计与细节。

**答案要点**：
- 四种格式、四个独立解析函数（`KNOWLEDGE_PARSERS` 字典注册），粘贴文本（`/import_knowledge_text`）与上传文件（`/upload_knowledge_file`）共用同一套解析器：
  - **JSON**：必须是数组，每项取 question/answer/keywords；
  - **TXT**：按**空行分块**，块内第 1 行问题、第 2 行答案、第 3 行（可选）关键词，少于 2 行的块丢弃；
  - **CSV**：首行若为 `问题`/`question` 表头则跳过；第 3 列及以后全部逗号合并为 keywords；
  - **Markdown**：按 `##`~`######` 标题分节（`re.split(r'^#{2,6}\s+', MULTILINE)`），标题行是问题、正文是答案。
- 文件上传按扩展名映射格式（md/markdown 同一解析器），UTF-8 容错解码（`errors='replace'`）；每条须同时有 question 和 answer 才入库；source 记为 `import_<fmt>` / `import_file`，操作成败写 `import_logs`（页面显示最近 50 条）。

**文件位置**：`app.py` L605-670（解析器）、L695-754（两个导入路由）。

### Q16. 用户反馈是怎么进入知识库的？这条链路的意义是什么？

**考察点**：数据闭环思维。

**答案要点**：
- `/submit_feedback`（公开接口，无需登录）：反馈必填 type/title/content，存 `feedback` 表。
- 若勾选"添加到知识库"复选框：**title 作为 question、content 作为 answer、keywords 留空、source='feedback'** 直接 INSERT 进 knowledge，并写一条导入日志"来自用户反馈的知识已入库"。
- 意义：形成"用户提问 → 未命中 → 反馈 → 管理员/用户补充 → 下次 RAG 直接命中"的闭环；且因为向量缓存按签名增量编码，新条目**下一次提问即自动被嵌入检索**，无需重启或手动重建索引。

**文件位置**：`app.py` L759-785。

## 七、高频追问

### Q17. 全量检索会不会成为性能瓶颈？怎么优化？

**答案要点**：
- 现状：每次提问把 knowledge 全表拉进内存，向量缓存避免了重复编码，但仍是**暴力精确检索（点积全量计算）**；条目达到几千条时 CPU 点积尚可（1024 维 × N 的矩阵乘），上万条后每次查询的编码+点积与每条的缓存加载都会变慢。
- README 已列的优化方向：向量索引升级为 FAISS ANN 索引；模型加载改为后台预热（现在首次提问要等 ~15 秒）；知识条目很多时 `_load_cached_vectors` 全表读 BLOB 可加内存缓存。
- 也可答：`_delete_stale_vectors` 每次检索都跑一次 DELETE，可改为仅在增删知识后触发。

### Q18. 这套系统有哪些安全短板？怎么改？

**答案要点**（README"仍可继续优化的方向"第 3 条 + 代码事实）：
- 管理员密码明文存环境变量/代码默认值（admin123）→ 改 bcrypt 哈希存储；
- API Key 明文存 settings 表 → 加密存储；
- 登录无验证码、无 CSRF 防护、无登录失败锁定 → 可加验证码/CSRF token；
- `run(debug=True)` 生产不能开（Werkzeug 调试器可执行代码）→ 生产用 waitress/gunicorn；
- 亮点可同时说：`login_required` 对 API 返回 401 JSON 的设计、密钥回显脱敏（前 4 后 4 位）已经做了。

### Q19. 如果要把"答案不参与向量编码"改成答案也参与，会有什么影响？

**答案要点**：
- 当前 `_signature()` 只含 `question|keywords`，动机：用户问题和知识条目的 question 是同构文本，语义匹配最准；答案通常更长，混入会稀释语义、且答案改动会触发大量无效重编码。
- 若要答案参与：需把 answer 加入签名，代价是答案任何微调都使向量失效重编码；更合理做法是 question 与 answer 分别编码/拼接加权，或对长答案引入 chunk 级检索。

### Q20. 用户选了 LLM 模式但知识库命中了（≥0.55），还会调大模型吗？

**答案要点**：
- **不会**。`get_answer()` 中 RAG 命中（top1 ≥ 0.55）直接 return，LLM 分支只在"未命中知识库"时进入——RAG 优先于大模型，省 token 且响应快；只有 0.30~0.55 之间的"擦边"结果才作为参考资料喂给大模型。追问点：这正是 RAG 的两种用法（检索直接答 vs 检索增强生成）在本项目中共存的体现。
